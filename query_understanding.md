# Query Understanding (QU)

## What is Query Understanding?

When a user types a search query, the raw text is ambiguous and noisy. Query Understanding
is the layer that converts this raw text into structured, machine-interpretable signals before
retrieval and ranking even start.

Example:
```
User types:  "entry level remote data engineer easy apply"
QU produces: { title: "data engineer", seniority: "entry", remote: true, easy_apply: true }
```

Without QU, the retrieval system would do keyword matching on the raw string. With QU, it
knows exactly what filters to apply and what the user actually wants.

---

## Building Blocks (the old way)

Before unified models, QU was a pipeline of separately trained components:

### 1. Entity Tagging (NER — Named Entity Recognition)

Identifies and labels specific pieces of text in the query.

```
"senior data engineer at Google in New York"
 └─ seniority: "senior"
 └─ title: "data engineer"
 └─ company: "Google"
 └─ location: "New York"
```

Traditional NER used encoder-only models (BERT-based). They were trained on a fixed vocabulary
of entity types. If a new entity type appeared (like "Easy Apply" or "hybrid"), you had to
retrain a separate model.

### 2. Query Routing (Intent Classification)

Determines what KIND of request the user is making, so the system routes it to the right path.

Examples:
- "data engineer jobs" → criteria query → extract tags, pass to retrieval
- "jobs near me" → self-referential query → needs member location before retrieval
- "how to write a resume" → unsupported intent → fallback to keyword search
- "find me illegal jobs" → trust violation → block

### 3. Query Rewriting

Transforms the user's query into a better retrieval string.

Use case: self-referential queries.
```
User:    "Find software engineer jobs near my location"
Profile: member is in San Francisco
Rewrite: "Find software engineer jobs near San Francisco, CA"
```

The rewritten query is what actually goes to the embedding/retrieval model, not the original.

### 4. Facet Suggestion

Recommends filters the user might want to add, shown as UI buttons.

```
Query: "data scientist"
Suggested facets: [Remote, Entry Level, Python, San Francisco]
```

These are generated by scoring candidate facets (from historical queries) against the current query.

---

## The Problem with Separate Models

Each component above was its own trained model. This creates:

1. **Error propagation**: if the tagger labels "easy apply" incorrectly, the rewriter makes
   wrong decisions based on that bad tag.

2. **No shared context**: the rewriter doesn't know what the tagger found. They're blind
   to each other.

3. **Long-tail failures**: a query like "salary > $150K remote ML roles in my network posted
   this week" has compound constraints. No single pipeline stage handles all of it reliably.

4. **Maintenance cost**: separate models = separate training pipelines, data, monitoring.

---

## The Unified Approach (LinkedIn's Paper)

Replace all components with a single SLM (1.5B params, Qwen2.5) that produces all outputs
in one forward pass.

### Two Generation Modalities — Not One JSON

The LLM operates in two modalities within a single streaming generation:

**Modality 1: Agentic Tool Calling** — used for Query Planner, Query Tagger, Facet Suggestion

Each attribute is a **separate tool call**. The LLM only calls the tools relevant to the query.
The "components" in Figure 1 are logical labels for groups of tool calls — not separate model
invocations.

```
LLM streams tokens (one forward pass) →

  tool_call: query_planner  → { route: "criteria" }       ← Query Planner
  tool_call: location_tool  → { location: "New York" }    ┐
  tool_call: company_tool   → { company: null }           │ Query Tagger
  tool_call: easy_apply_tool→ { easy_apply: true }        ┘
  tool_call: facet_tool     → { facets: ["Remote"] }      ← Facet Suggestion
```

**Modality 2: Text Rewriting** — used only for Query Rewriter (self-referenced route)

```
  plain text: "data engineer jobs near Bay Area, CA"      ← Query Rewriter
              (generated text, not a tool call)
```

The schema constraint applies **per tool call** — each tool has a fixed JSON schema it must
conform to. The LLM cannot hallucinate fields within a tool output or call tools not in its
definition list.

Table 1 in the paper measures each tool independently — `easy_apply_tool`, `date_posted_tool`,
`location_tool`, `company_tool` each have their own precision/recall. This is the real unit of
measurement, not a single monolithic JSON blob.

### Why Tool Calling, Not One Big JSON

One-JSON-for-everything would require the model to output every possible field on every query,
then null-fill the irrelevant ones. Tool calling lets the model call **only relevant tools** —
if the query doesn't mention easy apply, `easy_apply_tool` is never called. This keeps outputs
lean and reduces hallucination risk.

### Latency Trick: Parallel Tool Execution via Streaming

```
LLM streaming output:
  t=0ms:  [query_planner JSON complete]  → fire query_planner handler immediately
  t=80ms: [location_tool JSON complete]  → fire location_tool handler
  t=90ms: [company_tool JSON complete]   → fire company_tool handler (parallel with location)
  t=95ms: [easy_apply_tool complete]     → fire (parallel)
  t=200ms: full generation done

Without streaming: wait until t=200ms, then fire all handlers sequentially.
With streaming + custom JSON parser: handlers run concurrently, results ready by ~t=150ms.
```

A custom JSON parser reads the streamed tokens token-by-token and fires each tool the moment
its JSON is complete — no waiting for the full generation to finish.

### Why one model is better than separate models

The routing decision is generated FIRST (query_planner tool call), and subsequent tool calls
condition on it. A model that already "knows" the route is criteria will naturally attend to
attribute extraction. Tagger conditions on planner output implicitly — this shared context is
what a single model captures that a pipeline of separate models cannot.

## Query Illuminator

A key challenge: how do you get training labels for this unified model?

Labels are expensive — "correctness" in QU is not just semantic plausibility but also policy
compliance (don't hallucinate filters, don't over-extract, follow ambiguity handling rules).

**Query Illuminator** = a large offline LLM (8B) that serves two roles:

### Role 1: Teacher for Distillation
Given a query + context, the 8B model generates high-quality schema-constrained labels.
These become training data for the small 1.5B student model.

```
query → [8B Illuminator] → high-quality labeled output → training data for 1.5B SLM
```

This is knowledge distillation: the 1.5B model learns to mimic the 8B model's outputs,
not just hard labels (0/1) but soft probability distributions (captures uncertainty).

### Role 2: Surrogate Judge for Evaluation
Manual evaluation doesn't scale — you can't have humans label millions of queries.
The Illuminator evaluates model outputs using rubric-based scoring:
- facet extraction quality (did it get the right tags?)
- query hygiene (no hallucinated constraints?)

It scores outputs on a 0–4 graded scale, comparable to human expert agreement (κ = 0.77 vs
human ceiling of 0.83).

## How QU Outputs Flow Downstream

```
User Query
    │
    ▼
[QU: 1.5B SLM]
    │
    ├─ router = "criteria"
    ├─ tags = { title, location, company, remote, ... }
    ├─ rewrite = null
    └─ safety = null
    │
    ▼
Retrieval Layer (EBR bi-encoder)
    ├─ Structured tags injected into embedding prompt
    │   e.g., prompt += "Job Company: <COMPANY_NAME>"
    ├─ Tags used as hard filters (location, remote, easy_apply)
    └─ Rewrite used as retrieval string (if present)
    │
    ▼
Ranking Layer (SLM cross-encoder)
    └─ Tags used as additional features
```

Impact of injecting structured tags into retrieval prompt (from paper):
- Precision@50: +1.8%
- Recall@50:    +2.2%
- NDCG@50:      +1.7%

## Results at LinkedIn

Online A/B test on Semantic Job Search:
- Request failures: **-17.13%** (routing and tagging are more reliable)
- Search sessions: +0.74%
- Successful apply-or-save: +0.49%

Graded relevance in People Search (same model, different schema):
- Navigational queries: +57%
- Exploratory queries:  +75%


### Component 1: Query Planner

**What it does**: Classifies every query into one of 4 routes. This is the first token the LLM generates — everything downstream is conditioned on this decision.

| Route | Example | What happens |
|-------|---------|-------------|
| Criteria search | "remote ML engineer NYC" | → Query Tagger → Facet Suggestion |
| Non-job related | "I want to be a mermaid" | → Query Tagger (still tagged; may surface adjacent jobs) |
| Self-referenced | "jobs that match my qualifications" | → Query Rewriter (needs profile) |
| Trust violation | offensive/harmful content | → Request Failure immediately |

**ML system note**: Implemented as tool calling in the unified LLM, not a separate classifier. The route label is produced by the model's first generation step before any facet tokens are emitted. Precision = 0.994, Recall = 1.000 after fine-tuning (Table 1, query planner tool).

---

### Component 2: Query Tagger

**What it does**: Extracts structured attributes from the query. Replaces legacy NER models with generative LLM output constrained to a JSON/TypeScript schema.

**Tags extracted (tools)**:
```
title, company, location, seniority, remote, easy_apply,
date_posted, num_applicants, job_in_network
```

Each tag is a separate "tool" in the LLM tool-calling interface. The model calls only the tools relevant to the query — avoids hallucinating attributes not present.

**3 downstream uses of tags**:
1. **Hard filters** in Candidate Selection (e.g., location, remote=true, easy_apply)
2. **Input features** to Ranking Model (e.g., title, company as soft signals)
3. **UI Filter display** (surfaced as clickable filter chips)

**Fine-tuned vs pretrained performance (Table 1)**:
| Tool | Pretrained Recall | Fine-tuned Recall |
|------|-------------------|-------------------|
| easy_apply_tool | 0.100 | 1.000 |
| date_posted_tool | 1.000 | 1.000 |
| num_applicants_tool | 0.680 | 1.000 |
| job_in_network_tool | 0.960 | 1.000 |

**ML system note**: Streaming mode + custom JSON parser allows parallel tool execution as individual tools are recognized in the streamed output — reduces end-to-end latency significantly.

---

### Component 3: Query Rewriter

**What it does**: Transforms self-referential queries into explicit queries the retrieval system can handle.

**Inputs to the LLM call**:
- Raw query ("jobs near my location")
- Member Profile (location, title, skills, education, past roles, experience)
- Member Connection data (if job-in-network relevant)

**Output**: Rewritten string sent directly to Candidate Selection and Ranking.

```
"PM jobs that fit my qualifications"
→ "Product Manager jobs, 5+ years, fintech, San Francisco, CA"
```

**ML system note**: This is the only component that makes the member profile a first-class input to the LLM. The rewrite replaces the original query for retrieval embedding — not appended to it.

---

### Component 4: Facet Suggestion

**What it does**: Recommends filter options to show in the UI alongside search results (e.g., "Remote", "Entry Level", "Python").

**Design constraints**:
- Taxonomy is injected into the prompt — model can only suggest facets within the allowed taxonomy
- Only activated when specific signals are present (e.g., industry explicitly mentioned triggers related-industry facets)
- Personalized to member profile (avoids showing irrelevant facets)

**Output path**: → UI Filter layer (not to retrieval/ranking)

## Training Pipeline (ML Engineer Details)

### Model Choice

**Backbone**: Qwen2.5-1.5B-Instruct

Why 1.5B and not larger:
- P95 latency budget: 600ms end-to-end at thousands of QPS
- Models <2B met latency targets but hallucinated on structured output
- Models >7B unacceptably slow in production
- 1.5B sweet spot: high recall + structure fidelity after fine-tuning

### Fine-Tuning Strategy

**Algorithm: SFT (Supervised Fine-Tuning) — chosen over DPO**

SFT loss:
```
L_SFT = -sum(log P_θ(y_i | x_i))     where y_i = target structured output
```

Why SFT over DPO:
- DPO occasionally compromised format fidelity (valid JSON but wrong schema)
- SFT enforces strict structure adherence — critical for tool calling
- DPO preference pairs slow iteration; SFT faster MLOps cycle

**Multi-task instruction tuning (T0 framework)**:
- All 4 components share one model, trained jointly
- Task is selected per mini-batch — each mini-batch contains only one task type (**Homogeneous Batching**)
- Why not Heterogeneous Batching (random mix per batch): disjoint batches provide stable gradient signal per task; mixed batches cause conflicting gradient updates

**Data**:
- 3K–5K samples per task (human annotated + GPT-synthesized)
- GPT synthetic data: prompted with member context to generate realistic queries
- All synthetic samples reviewed by human annotators before training

**Hyperparameters**:
- Hardware: 2x H100 80GB, batch size 4 per device
- Optimizer: SGD with cosine scheduler
- Learning rate: 2e-5
- ~10 seconds per training step

## Serving Infrastructure (ML Engineer Details)

```
User Query
    │
    ▼
gRPC service (custom proxy, OpenAI Chat Completion API compatible)
    │
    ▼
vLLM engine (Qwen2.5-1.5B)
    │   - streaming mode ON
    │   - custom JSON parser (incremental, not wait-for-complete)
    │   - parallel tool execution as tools recognized in stream
    ▼
Multi-Instance GPU (A100 partitioned into isolated instances)
```

**Why vLLM**:
- Efficient KV cache sharing across requests (long system prompts with taxonomy/schema are shared prefix → PagedAttention reuse)
- Continuous batching handles variable decode lengths well
- Small decoder models with long shared prompt prefixes = ideal vLLM workload

**Latency optimization**:
- Streaming output: custom JSON parser reads token-by-token and fires tool calls as soon as a complete tool is parsed — doesn't wait for full JSON
- Parallel tool execution: if query has `location_tool` and `company_tool`, they execute concurrently as each is streamed and parsed
- This reduces P95 from ~900ms (wait for full response) to 600ms

**Throughput**:
- ~20 QPS per A100 GPU
- Multi-Instance GPU: single physical A100 split into isolated GPU instances, multiple model replicas

**Serving latency targets**:
| Metric | Value |
|--------|-------|
| Median latency | 400ms |
| P95 latency | 600ms |
| Throughput | ~20 QPS per A100 |

**Interface**: gRPC service behind a proxy compatible with OpenAI Chat Completion API → LangChain integration for tool calling framework
